# 0014. Непрерывная интеграция и анализ качества

[English version](0014-continuous-integration.md)

## Контекст

Проект обещает работать на Java 8 и более поздних JDK, как модули и как classpath. Сборка на одном JDK одной машины этого
не проверяет, а состояние проекта должно быть видно в начале README.

## Решение

- `.github/workflows/build.yml` запускается при каждом push в `master` и `develop` и при каждом pull request:
  - задание `build` выполняет `verify` на JDK 8, 11, 17, 21 и 25;
  - задание `sonar` собирает проект на JDK 21 и анализирует его в SonarCloud: организация `sftwnd-github`, проект
    `sftwnd_oracle_plsql_unwrapper`. Без секрета `SONAR_TOKEN` оно пропускает анализ и завершается успешно.
- `.github/workflows/native.yml` выполняет `verify` с профилем `native` на Windows, Linux и macOS и сохраняет каждый
  нативный файл артефактом вместе с `LICENSE`. Он запускается при push в `master`, при pull request, меняющем код или
  сборку, и вручную. Артефакт для Linux берётся из профиля `native-linux`: файлу, собранному на самой машине сборки, нужен
  её более новый glibc.
- Профиль Maven `coverage` включает JaCoCo. Каждый модуль записывает свои тесты, а модуль `oracle-plsql-unwrapper` строит
  один отчёт по всем модулям в `target/site/jacoco-aggregate`, который берёт анализ.
- README начинается с бейджей Java 8, JPMS, OSGi, порога качества, покрытия, сборки и лицензии.

## Обоснование

- Тесты запуска в `verify` уже запускают unwrapper на classpath и на module path, поэтому матрица JDK проверяет и то, и
  другое без отдельного задания.
- Классы модуля тестируются и из модулей, которые его используют: у SPI почти нет своих тестов, и отчёт по модулю занизил бы
  его покрытие.
- JaCoCo в профиле оставляет обычную сборку как есть на любом JDK, и проект `oracle-plsql-unwrapper-pro`, наследующий
  родителя, его не получает.
- Задание, проходящее без токена, не даёт бейджу сборки краснеть, пока SonarCloud не настроен.
- `native-image` собирает только под ту систему, где запущен, поэтому файлам других систем нужны машины этих систем. На
  Windows тот же запуск проверяет `native-image.cmd` и скрипт `bin\unwrapper.cmd`, которые больше никакая сборка не
  запускает.
- Нативная сборка занимает минуты на каждой системе, поэтому она не идёт при каждом push.

## Альтернативы

- **JaCoCo в каждой сборке.** Сборка медленнее и ещё один агент на каждом JDK ради отчёта, который читает только анализ.
- **Отчёт по модулю.** См. обоснование.
- **Бейджи Maven Central и javadoc.** Артефакты не опубликованы, бейджи были бы битыми.
- **Задание, запускающее jar на module path.** Оно повторяет тесты запуска.

## Последствия

- Анализ начнётся, когда проект появится в SonarCloud, а в репозитории будет секрет `SONAR_TOKEN`; до этого бейджи порога
  качества и покрытия ничего не покажут.
- Тесты запуска работают в отдельных JVM, поэтому покрытие их не учитывает.
- Проект `oracle-plsql-unwrapper-pro` приватный: такого workflow у него нет, а бейджи статические — Java 8, JPMS, OSGi и
  лицензия.
