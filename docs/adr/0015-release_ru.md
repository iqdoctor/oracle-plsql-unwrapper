# 0015. Выпуск

[English version](0015-release.md)

## Контекст

Библиотека попадает в Maven Central, где опубликованную версию нельзя ни удалить, ни заменить, а её исполняемые файлы —
к пользователям, у которых может не быть Java. Поэтому выпуск должен быть тем, что проверено, быть подписан и ещё раз
просмотрен до публикации. Проект `oracle-plsql-unwrapper-pro` наследует родителя этого проекта и никогда не должен попасть
в Maven Central.

## Решение

- У выпуска есть issue `Release X`. Pull request его ветки ставит версию `X` в `develop`; `develop` уходит в `master`
  через pull request, и merge-коммит в `master` получает аннотированный тег `vX`. Ещё один pull request переводит
  `develop` на следующий `SNAPSHOT`.
- Загрузка идёт из чистого клона тега: `./mvnw -Prelease clean deploy` на JDK 9 или новее, с ключом подписи,
  разблокированным в gpg-agent. Профиль `release`:
  - останавливает сборку, если версия не выпуска, JDK старше 9 или `central.skip` не `false`;
  - подписывает артефакты через maven-gpg-plugin;
  - загружает их через central-publishing-maven-plugin. Развёртывание ждёт в Central Publisher Portal в статусе validated
    и публикуется там вручную.
- В Maven Central попадают родительский POM и jar модулей `oracle-plsql-unwrap-spi`, `oracle-plsql-unwrap-v2` и
  `oracle-plsql-unwrapper`, каждый с исходниками, javadoc и тестами, и исполняемый jar unwrapper.
- Javadoc собирается каждой сборкой, с doclint и `failOnWarnings`; тег на каждый параметр и результат не требуется:
  комментарии — это фразы.
- Выпуск `vX` на GitHub содержит jar, zip-дистрибутив и нативные исполняемые файлы: для Linux x86_64, Windows x86_64 и
  macOS arm64 из workflow `native` ветки `master`, а для macOS x86_64 — собранный локально профилем `native`. Каждый
  нативный файл лежит в zip вместе с `LICENSE`.
- `oracle-plsql-unwrapper-pro` задаёт `central.skip=true`: профиль `release` там останавливается.

## Обоснование

- Тег на merge-коммите `master` называет ровно то, что выпущено, а загрузка из него повторяет проверенную сборку.
- Развёртывание в статусе validated ещё можно отбросить: проверка вручную перед публикацией занимает минуту и бережёт
  версию, которую нельзя забрать назад.
- central-publishing-maven-plugin загружает `SNAPSHOT` даже с `skipPublishing`, в репозиторий снимков портала, поэтому
  профиль отвергает `SNAPSHOT`, а не полагается на этот параметр.
- У GitHub нет машин macOS x86_64, поэтому этот файл собирается на такой машине.
- Версии меняются через pull request, как и любое другое изменение, и история сохраняет сообщения проекта.

## Альтернативы

- **maven-release-plugin.** Он сам коммитит и ставит тег со своими сообщениями и пушит до pull request.
- **autoPublish.** Ошибка, замеченная после загрузки, осталась бы в Maven Central навсегда.
- **Загрузка из GitHub Actions.** Ключ подписи и токен портала стали бы секретами репозитория.
- **Без проверки javadoc.** Битая ссылка незаметно попала бы на javadoc.io.

## Последствия

- Выпуску нужен владелец ключа: он разблокирует ключ перед загрузкой и публикует развёртывание после неё.
- Бейджи Maven Central и javadoc показывают версию только после публикации развёртывания.
- `deploy` без профиля `release` ничего не загружает: другого репозитория у проекта нет.
